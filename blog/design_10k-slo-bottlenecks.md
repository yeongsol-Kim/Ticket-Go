# 10,000 동시 부하 SLO 검증 — 병목의 연쇄

> 목표 SLO: **10,000명 동시 접속(플래시세일) × 2분 내 완료 × 오버부킹 0 × 승인 p95 < 1s**
> 환경: 앱 t3.small(2 vCPU / 2GB), 부하생성기 t3.small 2대(같은 VPC 내부망, 각 5,000 VU 분산)

---

## 0. 부하 생성 환경부터 — 왜 별도 EC2 2대인가

초기엔 맥에서 부하를 줬는데, t=0 동시 접속 폭증 시 **connection reset**이 수백 건 났다.
규명 결과 서버·커널·클라이언트 어느 쪽도 아니었고, **맥→공유기(NAT)→인터넷→EC2 네트워크 경로**가
순간 폭증을 못 버틴 것이었다(테스트 artifact, 서비스 결함 아님).

해결: **부하생성기를 앱과 같은 VPC에 두고 내부망(프라이빗 IP)으로 부하**. reset이 0으로 사라졌다.
이게 실무 표준(부하생성기를 대상과 같은 네트워크에 배치).

10,000 동시는 단일 t3.small(2GB)로는 k6 메모리가 부족(5,000 VU에 1.5GB) → **2대로 분산**
(각 5,000 VU, 서로 다른 유저 토큰 1~5000 / 5001~10000). 측정은 앱 DB `bookings.created_at`
span으로 통합(부하 출처 무관 자동 합산).

---

## 1. 병목 ①: Tomcat 연결 천장 8292

10,000명이 동시에 몰리자 booking이 **정확히 8292개에서 3회 연속 동일하게 캡**됐다.
나머지 1,708명은 `Broken pipe` / `ClientAbortException`으로 거부.

딱 떨어지는 8292는 우연이 아니었다:
```
maxConnections(8192, Spring Boot 기본) + acceptCount(100, 기본) = 8292
```
즉 처리율(스케줄러 ~94/s) 문제가 아니라 **연결 입구에서 막힘**. 5,000 동시(단일 부하생성기)는
8192 미만이라 안 걸렸고, 10,000에서 처음 드러났다.

**교훈**: 처리 로직만 최적화(벌크 A+B+D)해도, 그 앞단 **연결 수용 한계**가 먼저 막을 수 있다.

---

## 2. 병목 ① 돌파 → 병목 ②가 드러남

`server.tomcat.max-connections`를 8192 → 20000으로 올리자 **10,000명 전원 진입**.
워밍업 후 결과:

| 지표 | 결과 | SLO |
|---|---|---|
| 완주 시간 | ~108~118초 | ✅ (<120초) |
| 오버부킹 | 0 (재고 정확히 0) | ✅ |
| 성공률 / reset | 99.9% / 0 | ✅ |
| **승인 p95** | **~9.9초** | ❌ (<1s) |

문(연결)을 키우니 10,000명이 다 들어와서, 이제 **200 워커 스레드 / 20 DB 커넥션**을 두고
경쟁하게 됐다. 개별 승인 요청이 스레드·커넥션을 기다리며 지연 → 승인 p95 ~10초.

---

## 3. 병목 ②를 튜닝으로 뚫으려 시도 → U자 곡선

max-threads와 HikariCP 풀을 스윕(각 config 재시작 후 워밍업 4~5회로 플래토):

| max-threads / hikari-pool | 처리율 | 승인 p95 |
|---|---|---|
| 100 / 16 | ~91/s | ~13초 |
| **200 / 20 (Spring 기본값)** | **~92/s** | **~9.9초 ← 최소** |
| 500 / 50 | ~75/s | ~16초 (완주도 127~142초로 SLO 초과) |

**U자 곡선. 최소점이 Tomcat 기본값(200)에 정확히 위치.** 올려도 내려도 나빠졌다.

**원인 (2 vCPU 하드웨어)**:
- 스레드를 늘리면 진짜 병렬은 여전히 2개 → 컨텍스트 스위칭·경쟁만 증가
- HikariCP 풀을 늘리면 같은 2 vCPU의 MySQL에 동시 쿼리가 몰려 각 쿼리가 느려짐
  (HikariCP 위키의 "작은 풀이 더 빠르다"가 실측으로 확인됨)

---

## 4. 결론 — latency SLO는 하드웨어 한계

- ✅ **완주/정합성 SLO는 달성**: 10,000명 ~110초 완주, 오버부킹 0, 성공률 99.9%
- ❌ **승인 p95 < 1s는 t3.small에서 불가**: 최선(9.9초)도 SLO의 10배.
  튜닝으로 못 뚫는다(올려도 내려도 악화). 병목은 **설정이 아니라 2 vCPU 하드웨어**.

**뚫으려면**: (1) 더 큰 인스턴스, (2) 폴링 부하 감소 — 10,000명이 2초마다 상태 폴링 =
~5,000 req/s를 2 vCPU가 <1s로 쳐내는 건 물리적으로 어렵다. 폴링 주기를 늘리거나
push/SSE로 바꾸는 아키텍처 개선이 근본 해법.

**핵심 인사이트**: "스레드·커넥션을 올리면 성능이 오른다"는 흔한 오해를 실측으로 반박했다.
리소스 제약 환경에선 **기본값이 이미 잘 튜닝돼 있고, 진짜 병목은 하드웨어**다.
유효했던 유일한 튜닝은 `max-connections` 상향(연결 천장 제거)이고, threads/pool은
기본값 유지가 최선이었다.

---

## 적용된 설정 (application.yml, 전부 env로 조절 가능)

```yaml
server:
  tomcat:
    max-connections: ${SERVER_TOMCAT_MAX_CONNECTIONS:20000}  # 8192→20000 (플래시세일)
    accept-count:    ${SERVER_TOMCAT_ACCEPT_COUNT:1000}      # 100→1000
    threads:
      max:           ${SERVER_TOMCAT_THREADS_MAX:200}        # 200 유지 (최적)
```
